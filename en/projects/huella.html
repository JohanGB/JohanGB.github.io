01Problem

A passive, read-only profiler for Windows and Linux. It lives in the system tray, records use per application and detects memory leaks and processes with sustained CPU. Its principle: do not spend the resources it is trying to measure.

02Data

  • psutil readings every 10–15 s: CPU-time deltas, private memory and I/O per process, keyed by (pid, creation time) so reused PIDs are never mixed.
  • Aggregates per day and application are stored, not samples: the month is a GROUP BY.

03Method

  • One clock: only the collector thread has a timer; analyzer and writer wait on a queue without a timeout. That is why Gaming mode reaches zero.
  • A leak is three conditions on the per-minute minimum over 30 minutes: growth of at least 64 MB and 10 %, Kendall tau ≥ 0.70, and a Theil-Sen slope over the last third of at least 33 % of the total, which separates a leak from a cache that fills up.

04Validation

  • Gaming mode, 5 minutes: 0 ms CPU, 0 context switches and 0 KB written (daemon). Active: 0.04 % CPU and 22.6 MB RSS.
  • Disk: the real daemon wrote about 5.8 MB a day; in simulation, aggregates request 151 times less than one row per process and tick.
  • "Read-only" is tested: a test walks the code and fails if kill, terminate, subprocess, socket and similar appear.
  • 117 automated tests that pass in GitHub CI; one is flaky (it depends on real timing) and is pending review.

05Limitations

  • Figures are from Linux; on Windows it was only tested with test doubles, not on a real machine.
  • Zero CPU, not zero RAM: in Gaming mode the process stays in memory.
  • Leak thresholds were calibrated on synthetic series; a random walk triggers alerts in 2.3–6.1 % of cases.
